## HarnessRouter (Mori's agents)
- Mori runs as seven HarnessRouter Cloud harnesses in the "Default Workspace" (all `dsh` + `claude-sonnet-5.5`; ids, names and exact instructions in `harnessrouter.json` under `setups`, keyed by `feature_key`): six specialists, one per Ask Mori shortcut (price, order, grade, add, memory, tradeup), plus Ask Mori ("ask", every tool) for general questions. `MORI_RUNTIME=harnessrouter` turns it on (unset = AI Gateway, the rollback). Only /api/mori-chat uses it (it has the collector's session); the plain sendToMori RPC stays on AI Gateway.
- Routing is server-side and rules-based (`routeMoriMessage` in src/lib/mori-agents.ts, matching the shortcut templates' wording): a clear request goes to its specialist, anything else stays with the chat's current agent, or Ask Mori for a new chat. A specialist answering `role_mismatch` hands the message to Ask Mori. Switching agents passes the previous exchange as an "[App note: ...]". The browser never chooses a harness.
- Each agent keeps its own session per chat: `payload.hr = {agent, response_id, session_id}` on the turn's last text/status row in mori_messages; follow-ups send `previous_response_id` + `session_id` with that agent's own harness id. `user` is the Supabase user id.
- Tools: /api/mori-mcp?agent=<key> (MCP, stateless JSON) exposes only `AGENT_TOOLS[agent]` (Ask Mori: all 18). Auth: bearer derived from `MORI_MCP_SECRET` (stored in HarnessRouter as MCP secret `bindory-mori-tools`) plus the collector's Supabase session sealed with AES-GCM in `X-Mori-User` (10-minute expiry), so tools run under that collector's RLS. Chat cards come back HMAC-signed inside tool outputs and are verified before saving. Shell, write and web tools are disabled on every harness.
- Server env: `HR_API_KEY` (locally the one-line, git-ignored `.env.harnessrouter`), `MORI_MCP_SECRET`, `MORI_RUNTIME`. Never log or commit them.
- To change a harness: GET it by id and keep the ETag, update its entry in `harnessrouter.json`, PUT the full snake_case body with `If-Match`; on 412 fetch again and redo. `base` cannot change (create a new harness and replace every field of that entry). If an agent's tools change, change `AGENT_TOOLS` and the tool line in its instructions together (a test checks they match).
- Prices: TCGplayer US$ via TCGdex (src/lib/tcgdex.ts: `usdRange`, `priceScale`) plus recent eBay sold prices for raw NM, PSA 9 and PSA 10 from SilphCo Analytics (src/lib/silphco.server.ts, `SILPHCO_API_KEY`, free plan 2,000 lookups/month, 3 per card, cached 6 h). SilphCo is read with `marketplace=ebay` only, because its pooled prices include tokenised-card/NFT venues. SilphCo publishes no terms of use or licence yet: get written commercial terms before any public launch. Price checks by the Price Check agent show only a `price` chat card (lowest listing / market / mid scale, then recent sold raw NM / PSA 9 / PSA 10), rendered by `priceCardHTML` in wireframe/live.html and its built copy in wireframe/app.html; the reply text is dropped (its suggestions kept). Collectors never see price sources: not on the card, and agents never name marketplaces or providers, even when asked (founder decision, 2026-11-24).
- Sell orders need the collector's own front and back photos: without them the Orders agent calls `request_card_photos` (a `photos` chat row with Take a photo / Upload buttons using the wireframe's photo step, `PHOTO_SAYS.sell` added by scripts/build-wireframe.py), and the server replaces any sell-order card that has no photos with that request. Photos sent for a sell order are saved to the private memory-photos bucket at `<user id>/orders/` (status row `payload.photos`), attached to the sell card (shown through signed URLs), and stored with the order by `setup/012_order_photos.sql` (`market_orders.photo_paths`, `condition`). The agent reads the condition from the photos into `set_order.condition` (overall, centering front/back, each corner, edges, surface).
- Web search and fetch go through Telem (src/lib/telem.server.ts, `TELEM_API_KEY`, https://router.telem.ai/v1/search and /v1/fetch) as Mori tools `web_search` / `web_fetch` on /api/mori-mcp, never Telem's hosted MCP (it also exposes paid monitor tools). Only Ask Mori and Pre-grade may call them. Calls are capped: search on brave + tavily with 5 results each (about US$0.01), fetch at most 3 URLs and 6,000 characters each. Agents must state only what pages say and never take card prices from the web.
- Teamwork: every harness has a job description (mission, owns, not yours, receives, output, done when) and the same team roster with each teammate's key and hand-off prompts. Agents hand work over by offering a teammate's prompt in Suggestions; `routeMoriMessage` must send every roster prompt to its owner (a table test checks this). When the chat moves to another agent, the server sends an "[App note: hand-off ...]" with the card in focus (`cardInFocus`: newest price card, order/wishlist card, grade report or price lookup, with its catalogue id) and the last exchange. A specialist given a teammate's job answers `role_mismatch <key>` and the server reruns the message on that teammate (Ask Mori when no key). One owner per job: what to chase next belongs to Ask Mori, trends to Price Check.
- Adding a card names its binder: the chat template is `Add [card name] [card number] to my collection, in the binder "[binder]"` (pop-up lists the collector's binders or makes a new one). `add_card_to_collection` takes an optional `binder_name`; the proposal carries `binder {id?, name, new}` and on Confirm the browser files the card in that binder (creating a new one first) under the collector's RLS. HarnessRouter calls the tools on production (/api/mori-mcp), so tool changes only take effect after a deploy.
- "Sync from Collectr" (pop-up: public Collectr link + binder) sends `Sync my Collectr collection: <link> into the binder "X"` / `into a new binder called "X"`. It runs on its own harness, "Collection sync" (`feature_key: "collectr"` in harnessrouter.json, Hermes base, model gpt-6.1-sol), which reads the Collectr page in its browser and proposes the cards to add. `src/lib/collectr-sync.server.ts` starts it with `background: true` (tasks take minutes, longer than a request), saves a `kind: "sync"` row whose `payload.sync` holds response_id, session_id and an HMAC tying them to the collector, and /api/mori-sync (status | apply | file) polls, saves the answer and files, and adds the approved cards (exact catalogue matches only) into the chosen binder under RLS. A plain follow-up right after a finished sync continues that task (`previous_response_id`). Needs a model key for the harness's provider under HarnessRouter's Bring Your Own Key.
